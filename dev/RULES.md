# 개발 원칙

## 목적과 우선순위

- 궁극 목적은 유지보수성이다. 처음 보는 사람이 실행 경로, 변경 위치, 실패 원인, 복구 방법을 빠르게 이해할 수 있어야 한다.
- 업무 구현은 서비스에서 재사용하고, API·DB vendor·크론 호출 방식의 변경이 업무 구현의 복제로 이어지지 않게 한다.
- 명시적인 다중 문장 트랜잭션은 금지한다. 전체 원자성보다 안전한 재시도와 복구 가능성을 우선한다. (심층의도 : 인프라의 안정성을 보장하기 어려운 환경에서, 트랜잭션의 의존보다 재시도와 복구 가능성을 우선하는 것이 유지보수성에 유리하다.)
- 이 문서는 개발의 필수 기준이다. 충돌하는 요구나 구현 제약은 숨기거나 우회하지 말고 사용자에게 알린다.

## 메타 원칙

1. 유지보수성이 최우선이다. 코드 줄 수보다 이해 비용과 변경 위치 수를 줄인다.
2. 하나의 규칙에는 하나의 정의만 둔다. 업무 규칙, API 노출 정의, 저장 계약, 크론 호출 정의를 중복 작성하지 않는다.
3. 업무 로직은 서비스 레이어가 소유한다. API 연결부, Store, 크론 컨트롤러에 업무 판단을 분산하지 않는다.
4. 명시적인 트랜잭션보다 재시도·복구 가능성을 우선한다. 중단과 부분 완료를 전제로 설계한다.
5. DB vendor보다 서비스 계약이 먼저다. MySQL이나 다른 SQL DB를 사용해도 업무 의미와 저장 성공 조건이 유지되어야 한다.
6. 업무 판단과 값 가공은 서비스 레이어에서 한다. SQL에는 조회, 저장, 쓰기 조건만 둔다.
7. DRY, KISS, YAGNI를 따른다. 실제 중복과 변경 지점을 줄이는 공통화만 한다. 단일 용도 추상화와 예상 기능을 위한 확장 장치는 만들지 않는다.
8. 선언은 모으고 구현은 책임에 따라 둔다. API와 크론 연결 정보를 명시적으로 관리하고, 업무 구현은 해당 서비스 레이어에 둔다.
9. 실패 상태도 이해하고 재현할 수 있어야 한다. 성공, 조건 불일치, 일시 장애, 결과 미확인을 구분한다. 오류를 성공이나 빈 결과로 숨기지 않는다.
10. 각 실행 단위(API 요청·화면 로딩·배치 처리)는 목적 달성에 필요한 일만 수행한다. 하위 함수·DB 조회·외부 요청까지 포함해 처리량과 비용을 확인하고, 불필요한 반복·전체 순회·무거운 부수 작업을 줄이거나 분리한다.
11. 필요한 데이터 범위가 한정된 실행은 하위 함수의 반복·DB 조회·외부 요청까지 포함해, 전체 데이터·이력 증가에 비례하여 처리 비용이 커지지 않도록 한다. 상위 호출의 반환 건수만으로 판단하지 말고, 하위 처리까지 포함한 실제 처리량·호출 수·소요 시간으로 검증한다.
12. 각 실행 단위의 결과와 상태는 확인된 사실대로 표현한다. 미확인·부분 완료·처리 중·실패를 완료·성공·없음으로 단정하지 않는다.

## 서비스(서비스 레이어)·API 원칙

1. 서비스에 API 메타데이터를 부착한다. 별도 API 컨트롤 클래스와 독립된 컨트롤 레이어는 만들지 않는다.
2. 경로, HTTP 메서드, 입력 계약, 인증 요구, 응답 계약은 상수 또는 동등한 선언으로 관리한다. 동일 정의를 다른 파일에 중복 작성하지 않는다.
3. 공통 wrapper가 메타데이터에 따라 입력 검증, 인증 연결, 서비스 호출, 응답 변환을 수행한다.
4. wrapper에는 업무 분기, DB 접근, 업무 흐름 조합을 넣지 않는다.
5. 서비스는 HTTP 요청·응답 객체 없이 실행할 수 있어야 한다. 검증된 입력과 실행자 정보를 명시적으로 받는다.
6. 같은 서비스 함수를 API, 크론, 내부 호출에서 재사용한다.
7. 타입이 같은 입력·결과는 재사용하고, 다를 때만 명시적으로 변환한다. cast로 실제 형식 차이를 숨기지 않는다. 외부 입력은 실행 시 검증한다.
8. API 연결은 타입 검사와 코드 탐색이 가능해야 한다. 문자열 함수명에 의존한 동적 호출은 피한다.
9. 업무 결과와 공개 응답이 다르면 명시적으로 변환한다. DB 행이나 내부 상태를 자동으로 공개하지 않는다.
10. 업무 오류와 HTTP 표현을 분리한다. 서비스의 안정적인 오류 코드·결과를 공통 API 연결부에서 응답으로 매핑한다.
11. 컨트롤 클래스 없는 NestJS API 연결은 작은 구현으로 먼저 검증한다. 인증, 입력 검증, 예외 처리, 문서화가 적용되는지 확인하고 필요한 연결만 구현한다.

## Store·SQL 원칙

1. Store의 공개 계약은 특정 SQL DB vendor와 독립적으로 작성한다.
2. SQL 문법, 드라이버, ORM 타입, vendor 오류 처리는 DB adapter에 격리한다. 서비스에 노출하지 않는다.
3. 실행 코드의 SQL은 CRUD만 사용하고 SELECT 컬럼을 명시한다. 스키마 관련 작업이 필요하면 별도의 SQL 파일을 작성해 사용자에게 실행을 요청한다. 해당 SQL 파일은 커밋하지 않는다.
4. 모든 테이블의 기본키는 `id INT`로 한다. MySQL DDL은 signed 기본값의 `id INT NOT NULL AUTO_INCREMENT PRIMARY KEY`를 사용한다. 각 테이블에서 고유해야 하는 업무 키만 해당 테이블의 별도 UNIQUE로 보존한다.(bigint 가능)
5. WHERE, ORDER BY, LIMIT, JOIN은 허용한다.
6. SQL 값 가공, 집계, 계산, 형 변환은 금지한다. 집계는 SUM과 COUNT만 예외로 허용한다. 저장할 값은 애플리케이션에서 완성한다.
7. INSERT보다 UPSERT를 우선한다. 충돌 키와 갱신할 필드를 명시한다. 갱신이 기대 상태·버전에 의존하면 해당 조건을 원자적으로 검사하는 조건부 UPSERT(CAS)를 사용한다. (생성·갱신을 선택하기 위한 존재 확인 조회와 분기를 줄이고, 단일 문장으로 처리해 재시도·복구를 단순하게 하기 위함이다.)
8. vendor별 구현 방식이 달라도 조건부 쓰기의 의미는 같아야 한다. 조건부 upsert를 단순한 조회 후 저장으로 대체하지 않는다.
9. 쓰기 후 원하는 값이 저장되었는지 같은 쓰기 대상에서 확인한다. 캐시·replica를 검증에 사용하지 않는다.
10. 부분 갱신은 대상 필드만 쓴다. 읽어온 전체 행을 재저장해 다른 변경을 덮어쓰지 않는다.
11. Store는 저장과 조회를 담당하고, 업무 판단은 서비스가 담당한다. DB 표현을 TypeScript 값으로 변환하는 처리는 adapter에서 한다.
12. 지원하는 DB adapter는 실제 사용하는 upsert, 조건부 쓰기, 타입 변환, 저장 후 조회 계약을 동일한 기준으로 검증한다.
13. FOREIGN KEY와 CASCADE를 사용하지 않는다. 참조 유효성·수명·정리는 애플리케이션이 관리한다.
14. 시점은 Asia/Seoul 기준으로 저장·해석한다. 생성·파싱·DB 입출력·직렬화·비교·표시에서 시간대를 명시하며, DB·서버·로직·드라이버 등 다른 계층의 timezone이 달라도 저장값과 시점의 의미가 유지돼야 한다. 날짜만 있는 값은 시점과 구분한다.
15. 바이너리 타입 컬럼과 ASCII 문자셋을 사용하지 않는다.

## 재시도·충돌·복구 원칙

1. 명시적인 다중 문장 트랜잭션은 사용하지 않는다. 단일 쓰기의 원자성을 활용한다.
2. 같은 논리 작업의 재시도는 같은 작업 식별자와 저장 키를 사용한다.
3. 이미 완료된 작업을 다시 호출해도 중복 효과나 상태 후퇴가 없어야 한다.
4. 여러 단계 작업은 부분 완료 상태에서 이어서 실행할 수 있게 한다. 이미 완료된 단계는 건너뛰거나 동일 결과로 수렴한다.
5. 중요한 쓰기는 원자적인 조건으로 충돌을 막고, 재조회로 결과를 확인한다.
6. 조건 불일치는 최신 상태를 기준으로 다시 판단한다. 일시 장애와 같은 방식으로 무작정 재시도하지 않는다.
7. 응답 유실·시간 초과는 결과 미확인으로 취급하고, 기존 작업의 결과를 먼저 확인한다.
8. 외부 API, 메일, 결제 등도 재시도 시 중복 효과가 없도록 업무별 계약을 정한다.
9. 재시도 횟수와 종료 조건을 명시한다. 무한 재시도는 금지한다.
10. 복구는 남은 단계 완료 또는 취소 등 업무에 맞는 방향으로 정의한다. 여러 행의 전체 원자성을 단일 행 CAS로 보장한다고 가정하지 않는다.

## 크론 원칙

1. 크론 서비스 목록은 하나의 크론 컨트롤러에서만 관리한다. 이는 API 컨트롤 클래스 금지의 명시적인 예외다.
2. 각 항목에 작업 ID, crontab 표현식, 호출 함수, 시간대를 함께 선언한다.
3. 개별 서비스에 별도의 스케줄 정의나 스케줄 데코레이터를 두지 않는다.
4. 호출 함수는 타입 검사 가능한 참조로 연결한다.
5. 크론 컨트롤러는 호출을 관리하고, 업무 처리는 서비스에 위임한다.
6. 수동 실행과 예약 실행은 같은 서비스 함수를 사용한다.
7. 작업별 중복 실행 허용 여부와 이전 실행이 끝나지 않았을 때의 처리를 명시한다.
8. 재시도에서도 유지되는 예정 실행 시각과 작업 ID를 기준으로 실행을 식별한다.
9. 예정 시각, 실제 시작, 종료, 성공, 실패를 기록한다. 인증 정보와 시크릿은 기록하지 않는다.
10. 프로세스 재시작이나 장애로 놓친 실행을 재실행할지 건너뛸지 명시한다.
11. 여러 인스턴스에서 실행되는 경우에도 작업별 실행·중복 정책을 지킨다.
