# 개발 요청서 작성 규칙

## 목적과 적용 범위

- 기획 AI는 다른 AI 세션이 과거 대화 없이도 구현 범위, 요구 동작, 완료 조건, 미정 사항을 이해할 수 있도록 개발 요청서를 작성한다.
- 디자인·HTML·이미지만으로 알 수 없는 업무 의도와 조건을 보충한다. 빠진 내용을 추측으로 채워 확정하지 않는다.
- 이 문서는 요청서 작성과 전달 기준이다. 개별 요청서에는 해당 작업의 내용만 작성한다.
- 작업 규모에 맞게 작성한다. 단순 문구 수정에 복잡한 상태표나 장문의 양식을 요구하지 않는다.

## 작성 원칙

1. 필요한 결과와 이유를 작성한다. 요청 목적과 관계없는 기능이나 기술 설계를 추가하지 않는다.
2. 같은 대상은 같은 용어로 표현한다. 한 요구에는 한 가지 판단 가능한 내용을 작성한다.
3. 필수 요구, 참고 설명, 제안을 구분한다. "적절히", "정상적으로", "시안대로"만으로 요구나 완료 조건을 작성하지 않는다.
4. "앞서 정한 대로", "기존과 동일"처럼 다른 세션이 확인할 수 없는 표현을 사용하지 않는다. 필요한 내용을 요청서에 포함하거나 접근 가능한 자료와 위치를 특정한다.
5. 사용자 결정, 기존 확정 정책, 명시적으로 위임받은 판단을 근거로 확정 사항을 작성한다. AI가 만든 제안을 자동으로 확정하지 않는다.
6. 작업에 필요한 정보가 없으면 미정으로 남긴다. 양식을 채우기 위해 업무 정책, 수치, 동작, 제외 범위를 만들지 않는다.
7. 반복되는 설명은 한 곳에서 정의하고 참조한다. 여러 요구를 추적해야 할 때는 변경에도 유지되는 요구 ID를 사용한다.

## 요청서의 기본 내용

1. **목적:** 누가 어떤 상황에서 어떤 업무를 완료하려는지 작성한다.
2. **범위:** 이번에 변경할 화면·기능과 확인된 제외 범위를 작성한다. 미정 기능을 임의로 제외하지 않는다.
3. **기준 자료:** 전달 파일과 참조 자료의 목록, 용도, 기준 버전을 작성한다. 버전은 날짜나 파일명 등으로 식별할 수 있으면 충분하다.
4. **요구사항:** 사용자 행동, 실행 조건, 기대 결과, 화면·데이터의 변화를 작성한다.
5. **완료 조건:** 요구를 충족했는지 관찰할 수 있는 입력·행동·기대 결과를 작성한다.
6. **미정 사항:** 결정되지 않은 내용, 필요한 질문, 영향을 받는 범위를 작성한다. 없으면 "없음"으로 표시한다.

작업과 관련된 내용만 상세화한다. 해당하지 않는 항목마다 장문의 설명을 작성하지 않는다.

## 기능에 따른 보충 내용

- 입력 폼: 입력값, 필수 여부, 유효성 조건, 오류 표시, 제출 결과.
- 목록·검색: 데이터 출처, 검색·정렬·페이지 기준, 빈 결과와 조회 실패의 구분.
- 저장·삭제·외부 요청: 변경 대상, 허용 조건, 처리 중·실패·중복 실행·결과 미확인 시 사용자에게 보일 상태와 가능한 행동.
- 권한이 다른 기능: 실행 주체, 접근·조작 허용 범위, 허용되지 않을 때의 결과.
- 여러 화면 크기: 지원 범위, 배치·순서·숨김·스크롤의 변화.
- 팝업·복합 조작: 열기·닫기, 키보드 조작, 포커스 이동 등 필요한 상호작용.
- 금액·날짜·시간·파일: 단위, 형식, 제한, 표시 기준 등 결과에 영향을 주는 조건.

필요한 조건을 확인하지 못하면 미정으로 기록한다. 모든 기능에 모든 상태가 필요하다고 가정하지 않는다.

## 디자인·HTML·이미지 검토

1. 전달할 자료를 실제로 열어 확인한다. 읽지 못한 자료는 검토했다고 표시하지 않는다.
2. 각 자료가 구현 기준, 시각 참고, 현재 화면, 문제 재현, 실제 사용 자산 중 어떤 역할인지 작성한다. 하나의 자료에서 역할이 다르면 영역이나 동작별로 구분한다.
3. HTML의 배치·문구·상호작용 중 무엇을 따라야 하는지 명시한다. 샘플 데이터와 임시 동작을 실제 업무 요구로 자동 확정하지 않는다.
4. 이미지 전체 또는 특정 화면·영역 중 어디를 적용할지 특정한다. 여러 이미지가 있으면 파일명과 해당 요구를 연결한다.
5. 구현 판단에 중요한 문구·배치·순서 등은 요청서에도 명시한다. 세부 시각 정보 전체를 중복 전사하지 않는다.
6. 보이는 사실과 해석을 구분한다. 버튼이 보인다는 이유로 권한·저장 방식·이동 목적지를 확정하지 않는다. 이미지에 없는 상태를 기능이 없다는 뜻으로 해석하지 않는다.
7. 흐린 글자, 잘린 영역, 작은 아이콘 등 판독이 어려운 내용은 추측으로 확정하지 않는다. 확인할 수 없는 부분과 필요한 질문을 기록한다.
8. 정지 이미지로 확인할 수 없는 클릭·호버·포커스, 긴 문구, 데이터 증가, 화면 크기별 동작은 해당할 때 별도로 작성한다.
9. 시안에 보이는 로고·사진·아이콘과 실제 사용할 원본 자산을 구분한다. 필요한 자산의 제공 여부를 확인하고, 없으면 미확보로 기록한다.
10. 사용자에게 받은 원본 이미지를 AI가 재생성한 이미지로 임의 대체하지 않는다. 필요한 원본은 전달물에 포함한다.
11. 이미지·HTML·요청 문구가 다르면 확인된 기준을 명시한다. 기준을 결정할 근거가 없으면 충돌 내용과 질문을 남긴다.

## 확정·제안·미정 처리

- **확정:** 근거가 확인된 요구다. 근거는 요청서에서 식별할 수 있게 작성하며, 여러 요구가 같은 근거를 공유하면 한 번만 기록한다.
- **제안:** 기획 AI가 권하는 내용이다. 채택된 요구와 섞지 않는다.
- **미정:** 정보나 결정이 부족한 내용이다. 질문, 영향 범위, 확인된 경우 결정할 사람을 기록한다. 결정할 사람도 임의로 만들지 않는다.
- 단순 정보 누락과 구현자에게 위임한 선택을 구분한다. 위임한 경우 선택할 수 있는 범위와 지켜야 할 조건을 작성한다.
- 미정·충돌 때문에 진행할 수 없는 부분과 독립적으로 진행할 수 있는 부분을 구분한다. 의존성이 있는 부분을 임의 가정으로 구현하도록 요청하지 않는다.

## 완료 조건 작성

1. 핵심 요구를 충족했는지 확인할 수 있는 조건을 작성한다. 요구가 여러 개면 각 완료 조건이 어느 요구를 확인하는지 연결한다.
2. 업무 기능은 필요한 선행 조건, 사용자 행동, 관찰 가능한 결과로 표현한다. 시각 변경은 대상 화면·영역·상태와 기준 자료를 특정한다.
3. 해당 기능에서 중요한 실패·경계 사례를 포함한다. 정상 화면 하나만으로 전체 완료를 판단하지 않는다.
4. 수치 기준은 확인된 요구나 근거가 있을 때 작성한다. 검증 가능하게 보이도록 임의의 성능 수치나 시각 오차를 만들지 않는다.
5. 확인하지 않은 결과를 성공, 완료, 문제없음으로 표현하지 않는다. 문서 항목이 채워졌다는 사실과 요구 내용이 확인됐다는 사실을 구분한다.

## 생성과 전달

1. 요청서는 텍스트로 읽을 수 있는 독립 문서로 제공한다. Markdown을 권장하며, 일반 파일이나 대화 본문으로 작성해도 된다.
2. Claude Artifacts는 선택 사항이다. 사용할 경우에도 요청서와 시안을 구분하고, 다른 세션에서 읽을 수 있는 파일이나 본문으로 전달한다.
3. 요청서와 첨부물을 같은 전달 단위로 제공한다. ZIP이나 폴더 구조는 필수가 아니다.
4. 전달 목록에는 실제 파일명 또는 접근 가능한 위치와 용도를 작성한다. 작성자 컴퓨터의 절대경로만 적어 전달을 대신하지 않는다.
5. HTML에 필요한 CSS·스크립트·이미지 등도 전달하거나, 외부 의존성과 접근 조건을 명시한다.
6. 필요한 이미지 원본을 함께 전달한다. 이미지 설명이나 화면 미리보기만으로 원본 전달을 대신하지 않는다.
7. Artifact에서 보이는 자료가 내보낸 파일에도 포함됐다고 가정하지 않는다. 세션 내부 참조, 외부 주소, 누락된 자산을 확인한다. 확인할 수 없으면 미확인으로 기록한다.
8. 공유 링크를 사용할 수 있으나, 수신 세션의 접근 가능성을 가정하지 않는다. 요청 기준이 바뀌지 않도록 전달 버전을 식별하고, 필요한 경우 파일도 함께 제공한다.
9. 전달 메시지에는 먼저 읽을 요청서, 첨부 목록, 남아 있는 중요한 미정 사항을 짧게 적는다.

## 제출 전 검토와 변경

- 전달물만으로 목적·범위·요구 동작·완료 조건·미정 사항을 이해할 수 있는지 확인한다.
- 파일 목록과 실제 전달물을 대조하고, 자료의 역할·참조 위치·읽을 수 있는 상태를 확인한다.
- 디자인·이미지·HTML 사이의 충돌, 샘플을 정책으로 오인한 내용, 근거 없이 확정한 내용을 확인한다.
- 필수 항목을 채웠다는 이유로 누락이 없다고 단정하지 않는다. 검토한 범위와 확인하지 못한 내용을 구분한다.
- 요청이 바뀌면 요청서와 관련 첨부의 기준을 맞추고, 변경점과 영향을 받는 요구·완료 조건을 전달한다. 과거 대화에만 변경 사항을 남기지 않는다.
